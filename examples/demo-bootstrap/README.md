# ADEPT Deployment Bootstrap Container

**Purpose**: Dedicated tooling for production-ready two-VM ADEPT deployments with Let's Encrypt SSL and A2A gateway mesh.

**Key Features**:
- Let's Encrypt certificate generation (DNS-01 or HTTP-01)
- Artifact-based deployment (generate → review → apply)
- A2A gateway registration automation
- Full `agentic` CLI available
- Portable deployment tool

## Quick Start

### Prerequisites

**For Testing the Bootstrap Container** (see [TESTING.md](TESTING.md)):
1. **Base Image Built**:
   ```bash
   docker build -t agentic-framework-deps-base:latest -f Dockerfile.base .
   ```
2. **Bootstrap Container Built** (for integration tests):
   ```bash
   docker build -t demo-bootstrap:latest -f examples/demo-bootstrap/Dockerfile .
   ```
3. **Docker daemon running**

**For Using the Bootstrap Container** (generating deployment artifacts):
1. **ADEPT Services Running** (for A2A registration features):
   ```bash
   cd /path/to/adept-extended-2025-11-07
   make start
   ```

2. **Environment Variables** (loaded automatically from credentials):
   - `VALIDATION_RUNNER_CLIENT_ID`
   - `VALIDATION_RUNNER_CLIENT_SECRET`

**Note**: You can generate artifacts (certificates, configs, scripts) WITHOUT running ADEPT services. A2A registration features require running services.

### Generate Deployment Artifacts

```bash
# Create output directory
mkdir -p examples/demo-bootstrap/output

# Generate VM1 artifacts
docker compose -f examples/demo-bootstrap/docker-compose.bootstrap.yaml \
  --profile bootstrap run --rm demo_bootstrap deploy \
  --hostname vm1.api.agentic.local \
  --peer-hostname vm2.api.agentic.local \
  --vm1-ip 192.168.1.100 \
  --vm2-ip 192.168.1.101 \
  --email admin@example.com \
  --challenge dns

# Artifacts generated in: examples/demo-bootstrap/output/
```

### Review Generated Artifacts

```bash
ls -R examples/demo-bootstrap/output/

# Read deployment guide
cat examples/demo-bootstrap/output/DEPLOYMENT_GUIDE.md
```

## Architecture

### Component Overview

The bootstrap container is built on a **Python-based orchestration architecture** with clear separation between orchestration, business logic, and artifact generation.

#### Core Components

**1. Main CLI Orchestrator** (`bootstrap_main.py`)
- **Role**: Click-based CLI that provides 4 commands (`deploy`, `letsencrypt`, `a2a-register`, `a2a-list`)
- **What it does**: Coordinates Python modules, handles user input, logs progress
- **What it does NOT do**: Execute shell scripts or make system calls directly

**2. Python Business Logic Modules** (`modules/`)
- `artifact_generator.py` (278 lines) - Generates all 8 artifact types as files
- `letsencrypt_manager.py` (145 lines) - Certbot operations and certificate export
- `a2a_registrar.py` (153 lines) - A2A gateway registration with Keycloak auth

**3. Generated Shell Scripts** (OUTPUT artifacts in `/output/scripts/`)
- `apply-certificates.sh` - Copies certificates to ADEPT (generated by artifact_generator)
- `restart-services.sh` - Restarts ADEPT services (generated by artifact_generator)
- `register-{peer}.sh` - Registers peer gateway (generated by artifact_generator)

**4. Optional Utility Scripts** (`scripts/` - convenience wrappers)
- `setup-letsencrypt.sh` - User convenience wrapper (optional, not used by bootstrap_main.py)
- `register-peer-gateway.sh` - User convenience wrapper (optional, not used by bootstrap_main.py)

#### Critical Distinction

**Shell scripts in `/output/` are OUTPUTS, not dependencies:**
- bootstrap_main.py → Python modules → Generate shell scripts as artifacts
- User reviews artifacts → User runs generated scripts on VMs

**bootstrap_main.py does NOT:**
- ❌ Call shell scripts from `scripts/` directory
- ❌ Execute system commands directly (except certbot via subprocess)
- ❌ Run generated scripts automatically

**bootstrap_main.py DOES:**
- ✅ Import and call Python modules directly
- ✅ Generate shell scripts as text artifacts
- ✅ Coordinate multi-phase workflows (certificates → configs → A2A)

#### Execution Flow Example

```
User: docker run demo-bootstrap deploy --hostname vm1...
  ↓
bootstrap_main.py (CLI orchestrator)
  ↓ calls Python methods directly
  ├─ LetsEncryptManager.generate_certificate()
  ├─ LetsEncryptManager.copy_to_output()
  ├─ ArtifactGenerator.generate_env_updates()
  ├─ ArtifactGenerator.generate_hosts_entries()
  ├─ ArtifactGenerator.generate_cert_apply_script()  ← Generates shell script as text
  ├─ ArtifactGenerator.generate_a2a_registration_script()  ← Generates shell script as text
  └─ ArtifactGenerator.generate_deployment_guide()
  ↓
Artifacts written to /output/ directory (shell scripts, configs, certs)
  ↓
User reviews artifacts
  ↓
User manually runs generated scripts on VMs
```

### Artifact Generation Pattern

**Design Philosophy**: Container **generates artifacts** → User **reviews artifacts** → User **applies artifacts** to VMs

**NOT**: Container executes directly on VMs (security risk, no review step)

### Artifact Types

| Artifact | Location | Purpose |
|----------|----------|---------|
| SSL Certificates | `/output/certs/*.crt,*.key` | HTTPS for nginx |
| Renewal Hook | `/output/certs/renewal-hook.sh` | Auto-renewal |
| Env Updates | `/output/configs/env-updates.sh` | Update PUBLIC_HOSTNAME |
| Hosts Entries | `/output/configs/hosts-entries.txt` | DNS resolution |
| A2A Payloads | `/output/a2a/register-*.json` | Gateway registration |
| A2A Scripts | `/output/a2a/register-*.sh` | Register peer |
| Deployment Guide | `/output/DEPLOYMENT_GUIDE.md` | Step-by-step instructions |

## Output Directory Structure

### Version Control Strategy

**Directory**: `examples/demo-bootstrap/output/`

**Git Configuration**:
- ✅ `.gitkeep` - Ensures directory is tracked in version control
- ✅ `.gitignore` - Ignores ALL generated artifacts
- ❌ **Certificates, keys, scripts** - NEVER committed to git

**Why This Pattern**:
1. **Directory exists in git** - Developers clone repo and directory is ready
2. **Artifacts are ignored** - Certificates and secrets never accidentally committed
3. **Clean git status** - No untracked artifact files cluttering `git status`

**Generated Directory Structure** (all gitignored except .gitkeep):
```
output/
├── .gitkeep          # Tracked in git ✅
├── .gitignore        # Tracked in git ✅
├── certs/            # Generated, ignored ❌
│   ├── *.crt        # SSL certificates (NEVER commit)
│   ├── *.key        # Private keys (NEVER commit)
│   └── renewal-hook.sh
├── configs/          # Generated, ignored ❌
│   ├── env-updates.sh
│   ├── hosts-entries.txt
│   └── nginx-ssl.conf
├── scripts/          # Generated, ignored ❌
│   ├── apply-certificates.sh
│   ├── apply-configs.sh
│   └── restart-services.sh
├── a2a/              # Generated, ignored ❌
│   ├── register-*.json
│   └── register-*.sh
└── DEPLOYMENT_GUIDE.md  # Generated, ignored ❌
```

**Verification**:
```bash
# Check git ignores artifacts correctly
cd examples/demo-bootstrap
echo "test cert" > output/test.crt
git status output/
# Expected: Shows only .gitkeep and .gitignore, NOT test.crt

# Clean up test file
rm output/test.crt
```

## Usage Examples

### Full Two-VM Deployment

```bash
# === Step 1: Generate VM1 Artifacts ===
docker compose -f examples/demo-bootstrap/docker-compose.bootstrap.yaml \
  --profile bootstrap run --rm demo_bootstrap deploy \
  --hostname vm1.api.agentic.local \
  --peer-hostname vm2.api.agentic.local \
  --vm1-ip 10.0.1.100 \
  --vm2-ip 10.0.1.101 \
  --email admin@example.com \
  --challenge dns

# Save VM1 artifacts
mv examples/demo-bootstrap/output examples/demo-bootstrap/output-vm1

# === Step 2: Generate VM2 Artifacts ===
docker compose -f examples/demo-bootstrap/docker-compose.bootstrap.yaml \
  --profile bootstrap run --rm demo_bootstrap deploy \
  --hostname vm2.api.agentic.local \
  --peer-hostname vm1.api.agentic.local \
  --vm1-ip 10.0.1.100 \
  --vm2-ip 10.0.1.101 \
  --email admin@example.com \
  --challenge dns \
  --output-dir /output

# Save VM2 artifacts
mv examples/demo-bootstrap/output examples/demo-bootstrap/output-vm2

# === Step 3: Review Artifacts ===
cat examples/demo-bootstrap/output-vm1/DEPLOYMENT_GUIDE.md

# === Step 4: Transfer to VMs ===
scp -r examples/demo-bootstrap/output-vm1/ user@vm1:/tmp/adept-artifacts
scp -r examples/demo-bootstrap/output-vm2/ user@vm2:/tmp/adept-artifacts

# === Step 5: Apply on VM1 ===
ssh user@vm1
cd /tmp/adept-artifacts

# Apply /etc/hosts
sudo tee -a /etc/hosts < configs/hosts-entries.txt

# Apply certificates
./scripts/apply-certificates.sh /path/to/adept

# Update configuration
./configs/env-updates.sh /path/to/adept/.env

# Restart services
./scripts/restart-services.sh /path/to/adept

# Register peer
cd /path/to/adept
source deployment/local/docker-compose/.env-keycloak-credentials-dir/.env-keycloak-credentials
/tmp/adept-artifacts/a2a/register-vm2-gateway.sh

# === Step 6: Repeat on VM2 ===
```

## Deployment Workflows

### Workflow A: Centralized Generation (Recommended)

**Best for**: Multi-VM deployments with consistent configuration

```
Laptop/Workstation
  ├─ Generate VM1 artifacts → output-vm1/
  ├─ Generate VM2 artifacts → output-vm2/
  ├─ Review artifacts locally
  └─ Transfer to VMs

VM1 ← Apply artifacts from output-vm1/
VM2 ← Apply artifacts from output-vm2/
```

**Advantages**:
- Review before apply (security)
- No container runtime on VMs needed
- Version control artifacts (git)
- Consistent generation environment

### Workflow B: Per-VM Generation

**Best for**: Independent VM deployments

```
VM1
  ├─ Run bootstrap container
  ├─ Generate artifacts locally
  └─ Apply immediately

VM2
  ├─ Run bootstrap container
  ├─ Generate artifacts locally
  └─ Apply immediately
```

**Advantages**:
- Self-contained per VM
- No artifact transfer needed
- Faster for single-VM updates

## Let's Encrypt Certificate Management

### Challenge Types

**DNS-01** (Recommended for internal FQDNs):
```bash
--challenge dns
```
- Works for internal/private networks
- Requires DNS provider access
- Manual TXT record creation

**HTTP-01** (Requires public port 80):
```bash
--challenge http
```
- Automatic validation
- Requires public internet access
- Port 80 must be open

### Reusing Existing Certificates

If you have existing Let's Encrypt certificates:

**Option A: Renew with New Domain**
```bash
certbot certonly --manual --preferred-challenges dns \
  -d vm1.api.agentic.local \
  --cert-name vm1-agentic
```

**Option B: Copy Existing Certificates**
```bash
# On VM with existing certs
sudo cp -r /etc/letsencrypt/live/OLD_DOMAIN/ \
           /etc/letsencrypt/live/vm1.api.agentic.local/

# Run bootstrap to export
docker compose -f examples/demo-bootstrap/docker-compose.bootstrap.yaml \
  --profile bootstrap run --rm demo_bootstrap letsencrypt \
  --hostname vm1.api.agentic.local \
  --email admin@example.com
```

**Option C: Manual Copy**
```bash
mkdir -p examples/demo-bootstrap/output/certs
sudo cp /etc/letsencrypt/live/OLD_DOMAIN/fullchain.pem \
        examples/demo-bootstrap/output/certs/vm1.api.agentic.local.crt
sudo cp /etc/letsencrypt/live/OLD_DOMAIN/privkey.pem \
        examples/demo-bootstrap/output/certs/vm1.api.agentic.local.key
chmod 644 examples/demo-bootstrap/output/certs/*.crt
chmod 600 examples/demo-bootstrap/output/certs/*.key
```

### Certificate Renewal

Certificates expire every 90 days. Renewal is automated:

```bash
# Install renewal hook (from generated artifacts)
sudo cp /tmp/adept-artifacts/certs/renewal-hook.sh \
        /etc/letsencrypt/renewal-hooks/deploy/adept-reload.sh
sudo chmod +x /etc/letsencrypt/renewal-hooks/deploy/adept-reload.sh

# Setup cron (twice daily)
(sudo crontab -l 2>/dev/null; echo "0 0,12 * * * certbot renew --quiet") | sudo crontab -
```

## IP Address vs FQDN

### Recommendation: Use FQDNs

**Why**:
- SSL certificates require FQDN (not IP)
- nginx `server_name` needs hostname
- Keycloak redirect URIs use https://hostname
- A2A discovery uses URLs

**Setup** (generated by bootstrap):
```bash
# /etc/hosts on BOTH VMs
192.168.1.100  vm1.api.agentic.local
192.168.1.101  vm2.api.agentic.local

# Use FQDNs everywhere
PUBLIC_BASE_URL=https://vm1.api.agentic.local
```

### Alternative: Self-Signed Certs (Testing Only)

If you must use IPs:
- Skip Let's Encrypt
- Use self-signed certs with IP SANs
- Disable SSL verification (`verify=False`)

**Not recommended for production.**

## Module Reference

### `bootstrap_main.py` (Main CLI Orchestrator)

**Purpose**: Click-based CLI orchestrator that coordinates all Python modules

**Role**: Entry point for all container operations (NOT a module, but the main executable)

**Commands**:
- `deploy` - Full two-VM workflow (coordinates all 3 modules)
- `letsencrypt` - Certificate-only operation (uses letsencrypt_manager)
- `a2a-register` - Register peer gateway (uses a2a_registrar)
- `a2a-list` - List registered peers (uses a2a_registrar)

**Key Implementation Details**:
- Imports Python modules directly (lines 33-35)
- Calls module methods, not shell scripts
- Handles CLI argument parsing with Click decorators
- Provides user-facing logging and progress messages
- Orchestrates multi-phase workflows (cert generation → config → A2A)

**What it does NOT do**:
- Does NOT call shell scripts from `scripts/` directory
- Does NOT execute generated scripts automatically
- Does NOT make direct system calls (except certbot via modules)

**Example Flow** (deploy command):
```python
# bootstrap_main.py lines 47-129
@cli.command()
def deploy(...):
    artifact_gen = ArtifactGenerator(output_dir)
    le_manager = LetsEncryptManager(hostname, email, challenge_type=challenge)

    # Phase 1: Certificate operations
    le_manager.copy_to_output(f"{output_dir}/certs")
    le_manager.generate_renewal_hook(f"{output_dir}/certs")

    # Phase 2: Configuration artifacts
    artifact_gen.generate_env_updates(hostname)
    artifact_gen.generate_hosts_entries(...)
    artifact_gen.generate_cert_apply_script(hostname)

    # Phase 3: A2A artifacts
    artifact_gen.generate_a2a_registration_script(...)

    # Phase 4: Documentation
    artifact_gen.generate_deployment_guide(...)
```

### `artifact_generator.py`

**Purpose**: Generate all deployment artifacts

**Methods**:
- `generate_env_updates(hostname)` - Shell script to update .env
- `generate_hosts_entries(vm1_hostname, vm1_ip, vm2_hostname, vm2_ip)` - /etc/hosts entries
- `generate_cert_apply_script(hostname)` - Script to copy certs to ADEPT
- `generate_a2a_registration_payload(alias, public_url, description, tags)` - JSON payload
- `generate_a2a_registration_script(alias, public_url, description, tags)` - Shell script
- `generate_restart_script()` - Script to restart services
- `generate_deployment_guide(vm1_hostname, vm2_hostname)` - Markdown guide

### `letsencrypt_manager.py`

**Purpose**: Let's Encrypt certificate operations

**Methods**:
- `generate_certificate()` - Run certbot to generate cert
- `copy_to_output(output_dir)` - Export cert to artifacts
- `generate_renewal_hook(output_dir, adept_root)` - Create renewal script
- `test_renewal()` - Dry-run renewal test

### `a2a_registrar.py`

**Purpose**: A2A gateway registration

**Methods**:
- `get_auth_token()` - Get JWT from Keycloak
- `register_peer(alias, public_url, description, tags)` - Register gateway
- `list_peers()` - List all registered gateways
- `test_connection(alias)` - Test connectivity to peer

## A2A Gateway Architecture

### Internal vs External Access Patterns

**Important**: gateway_registry is an INTERNAL service. External access must use nginx_proxy routing.

| Access From | Registry URL | Endpoint |
|-------------|--------------|----------|
| Docker services | `http://gateway_registry:8086` | `/v1/gateways/` |
| Host/External | `https://api.agentic.local/internal/registry` | `/gateways/` (nginx rewrites) |
| Custom hostname | `https://${PUBLIC_HOSTNAME}/internal/registry` | `/gateways/` |

**Architecture**:
- External clients → nginx_proxy (443) → gateway_registry (8086)
- Only ports 80 and 443 exposed externally
- nginx rewrites `/internal/registry/` → `/v1/` before proxying

**Examples**:
```bash
# ✅ CORRECT - External access via nginx_proxy
curl -H "Authorization: Bearer $TOKEN" \
  https://api.agentic.local/internal/registry/gateways/

# ✅ CORRECT - Internal access from Docker services
curl -H "Authorization: Bearer $TOKEN" \
  http://gateway_registry:8086/v1/gateways/

# ❌ WRONG - Direct port access from host (bypasses nginx)
curl -H "Authorization: Bearer $TOKEN" \
  http://localhost:8086/v1/gateways/
```

## Security Considerations

### Artifact Review

**ALWAYS review generated artifacts before applying**:
```bash
# Check all generated files
find examples/demo-bootstrap/output/ -type f -exec head -20 {} \;

# Verify no hardcoded secrets
grep -r "password\|secret\|key" examples/demo-bootstrap/output/
```

### Credential Isolation

- Container doesn't store/transmit credentials
- Credentials only used for runtime A2A registration
- All operations use volume-mounted credentials (read-only)

### Privileged Access

- Container does NOT need SSH or VM access
- Container does NOT need sudo/root on host
- All operations are artifact generation only
